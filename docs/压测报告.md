## 1. 结论摘要

本次对初版部署进行了本机回环压测，覆盖 Nginx 静态资源、Go API、Nuxt SSR 首页三类请求。

### 1.1 QPS 在哪里看

**报告里所有表格的「QPS（req/s）」列就是 QPS。**

QPS 的意思是：**每秒成功处理多少个请求**。数字越大，说明服务器每秒能服务的人越多。

看报告只需要重点关注三列：

| 指标 | 含义 | 怎么看 |
| --- | --- | --- |
| QPS（req/s） | 每秒处理的请求数 | 越大越好 |
| P95 延迟 | 95% 的请求在这个时间内返回 | 越小越好，比平均值更能反映卡不卡 |
| 失败 | 失败请求数 | 0 最好，非 0 说明有错误 |

### 1.2 一句话结果

| 场景 | 峰值 QPS（req/s） | P95 延迟 | 失败率 | 结论 |
| --- | --- | --- | --- | --- |
| 管理后台静态资源 | 约 15,095 | 7 ms | 0% | 余量很大 |
| Go 健康检查 `/ping` | 约 5,836 | 15 ms | 0% | 余量很大 |
| Go API `site/config` | 约 2,276 | 78 ms | 0% | 余量较大 |
| 官网首页 SSR `/` | 约 79 | 779 ms（50 并发） | 0% | 主要瓶颈 |

### 1.3 用大白话解释

- **管理后台和静态文件**：每秒能处理约 1.5 万个请求，非常快。
- **Go 接口**：每秒约 2 千多个请求，性能充足。
- **官网首页**：每秒约 80 个请求。50 个人同时刷新首页时，95% 的请求在 0.78 秒内返回。
- 所有测试都是 0 失败，说明服务器没有崩、没有报错。
- 真正需要关注的是官网首页，因为每次访问都要由 Nuxt 现场生成 HTML，比静态文件和接口慢很多。

总体判断：

- **2 核 3.6G 服务器可以稳定支撑初版的小流量官网。**
- 静态资源和 Go API 性能余量充足。
- **Nuxt SSR 是当前主要瓶颈**：单实例约 60–80 QPS，并发升高后延迟明显增长。
- 内存峰值约 1.3 GB，未出现 OOM、容器重启或请求失败。
- 当前服务器未配置 Swap，建议补 1–2 GB 作为兜底。

## 6. 分析

### 6.1 静态资源

`/admin/` 由 Nginx 直接返回，吞吐 1.4–1.5 万 req/s，延迟个位数毫秒，性能充足。官网的 JS / CSS / 图片等静态资源预计也是同一水平。

### 6.2 Go API

`/ping` 和 `site/config` 均表现稳定：

- 健康检查峰值约 5,800 req/s
- 业务 API 在 100 并发下约 2,200 req/s，P99 约 108 ms
- 未出现错误或超时

Redis 渲染缓存和 MySQL 查询没有成为瓶颈。当前 API 性能足够支撑初版流量。

### 6.3 Nuxt SSR

首页 SSR 是唯一明显瓶颈：

- 单实例约 60–80 req/s
- 2 核服务器上，Node 进程主要吃单核，CPU 先饱和
- 并发 50 时 P95 已达 779 ms
- 页面区块越多、图片越多，SSR 时间还会增加

这不代表“只能支持 80 个用户”，因为用户不会每秒都请求一次页面；但遇到推广、活动或搜索引擎抓取高峰时，首页可能出现明显等待。

## 7. 容量建议

### 7.1 当前配置适用场景

| 场景 | 判断 |
| --- | --- |
| 日常企业官网，访问量低 | 足够 |
| 后台日常编辑、素材上传 | 足够 |
| 几十人同时在线浏览 | 基本可用 |
| 上百人同时访问首页 | 建议优化或扩容 |
| 活动推广、短时高并发 | 需要 CDN / 页面缓存 / 多实例 |

### 7.2 优化优先级

1. **静态资源走 CDN**
   - `/_nuxt/*`、`/uploads/*`、图片和视频
   - 可显著降低 Nginx 和服务器带宽压力

2. **给首页增加页面级缓存**
   - 页面内容发布后变化不频繁，可做短 TTL 的整页缓存
   - 命中缓存时不再执行 Nuxt SSR

3. **前端多实例**
   - Nuxt SSR 无状态，可以在 Nginx 后增加多个 frontend 副本
   - 2 核服务器不建议同时跑多个 Node 副本，优先加 CPU 或换 4 核

4. **开启压缩**
   - Nginx 开启 gzip / brotli，减少 HTML、JS、CSS 传输体积

5. **补 Swap**
   - 当前未配置 Swap
   - 建议增加 1–2 GB，防止极端内存波动导致进程被系统杀掉

6. **持续监控**
   - 关注 P95 延迟、5xx 比例、容器内存、磁盘和素材增长
   - 访问量上来后重新压测

## 8. 测试限制

本报告结论基于以下条件，实际线上表现可能不同：

- 从服务器本机发起，未经过公网和带宽限制
- 只测试 GET 请求，未测试登录、保存页面、上传视频等写操作
- 只测试 HTML 响应，未包含浏览器加载 JS / CSS / 图片的耗时
- 首页内容复杂度为当前已发布页面，区块和图片增多会降低 SSR 吞吐
- 未启用 HTTPS / TLS
- 单机单实例，未测试多副本和 CDN
- 测试时长较短，未做长时间稳定性浸泡

---

## 9. 最终结论

当前 **2 核 3.6G** 服务器可以满足初版官网的低流量运行：

- 静态资源与 Go API 性能充足
- 数据库与 Redis 资源占用正常
- 无失败请求、无容器重启、无错误日志
- 主要风险在 Nuxt SSR 单实例吞吐和未来素材磁盘增长

建议保持当前配置上线，同时优先做 **静态资源 CDN、首页缓存和 Swap 兜底**。如果后续推广带来明显流量，优先升级 CPU 或增加前端实例，而不是只加内存。
